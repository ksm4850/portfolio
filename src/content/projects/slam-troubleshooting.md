# 문제 해결

### 1. Celery 이벤트로 인한 비정상 브로커 트래픽 개선

**현상** — RabbitMQ 송신 트래픽이 실제 태스크 처리량 대비 비정상적으로 높은
평균 400kB/s로 지속 발생.

![문제 당시 — 송신 트래픽 약 400kB/s 지속](projects/medias/play/rabbitmq1.png)

**원인 분석** — RabbitMQ 관리 UI를 확인해 보니 `celeryev.*` 큐가 40개 이상 생성되어
있었고 큐마다 초당 15개 메시지가 흐르고 있었습니다. 약 40개의 Celery 워커 인스턴스가
각자 태스크 이벤트·gossip·mingle·heartbeat 메시지를 브로커로 발행하며 트래픽이
누적된 것이 원인이었습니다.

**조치** — 모니터링에 쓰지 않는 워커 이벤트(`worker_send_task_events`,
`task_send_sent_event`)와 워커 간 동기화 메시지(gossip·mingle·heartbeat)를 전부
비활성화하고, 남아 있던 `celeryev.*` 큐를 정리했습니다.

**결과** — 송신 트래픽 평균 **400kB/s → 3.2kB/s (약 99% 감소)**, 이벤트 큐 재생성 없이
정상 운영 확인.

![조치 후 — 송신 트래픽이 3.2kB/s 수준으로 감소](projects/medias/play/rabbitmq2.png)

### 2. DGX-Spark 온프레미스 원박스 배포

**요구사항** — 전체 서비스 스택을 단일 장비(DGX-Spark)에 담아 고객사에 반입하고,
전원만 켜면 즉시 운영되는 "원박스" 솔루션이 필요했습니다.

**문제** — 고객사 내부는 외부와 단절된 폐쇄망이라 사전에 IP를 알 수 없고, 네트워크가
바뀔 수도 있는데 API 호출 주소·CORS 등이 호스트 IP에 의존합니다. 고객사 측의 수동
설정 개입은 최대한 배제해야 했습니다 (문제가 생겨도 재부팅으로 해결되도록).

**해결** — 부팅 시 실행되는 init 스크립트를 작성해, PC가 재시작될 때마다 호스트 IP를
감지·기록하고 Docker Compose 전체 스택(파일 스토리지는 MinIO)이 해당 IP 기준으로
자동 기동되도록 구성했습니다. 네트워크가 바뀌어도 재부팅 한 번이면 전 서비스가
새 IP에 맞춰 올라옵니다.
