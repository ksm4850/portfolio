# 문제 해결

### 1. Celery 이벤트로 인한 비정상 브로커 트래픽 개선

**구조 배경** — 프로젝트마다 학습되는 모델이 다르기 때문에, 추론은 해당 프로젝트의
모델을 적재한 전용 컨테이너로 띄워야 합니다. 즉 워커 수가 동시 처리량이 아니라
**프로젝트 수에 비례해 증가**하고, 서비스가 성장할수록 워커도 계속 늘어납니다.

**현상** — RabbitMQ 송신 트래픽이 실제 태스크 처리량 대비 비정상적으로 높은
평균 400kB/s로 지속 발생.

![문제 당시 — 송신 트래픽 약 400kB/s 지속](projects/medias/play/rabbitmq1.png)

**원인 분석** — RabbitMQ 관리 UI를 확인해 보니 `celeryev.*` 큐가 40개 이상 생성되어
있었고 큐마다 초당 15개 메시지가 흐르고 있었습니다. Celery는 gossip이 켜져 있으면
모든 워커가 서로의 이벤트를 구독하는 소비자가 되어 워커마다 `celeryev.*` 큐가 하나씩
생기고, 각 워커의 heartbeat 이벤트가 그 큐 전부로 복제됩니다. 결국 트래픽이 워커 수의
제곱에 비례해 늘어나는 구조라, 태스크 처리량과 무관하게 40개 워커의 상호 동기화
메시지만으로 400kB/s가 상시 발생하고 있었습니다.

**조치** — 해당 옵션들의 기본값은 워커 수가 적고 Flower 등 이벤트 기반 모니터링을
쓰는 환경을 전제로 켜져 있습니다. 하지만 프로젝트마다 워커가 늘어나는 이 구조에서는
워커가 추가될수록 비용만 커지므로, 모니터링에 쓰지 않는 워커 이벤트
(`worker_send_task_events`, `task_send_sent_event`)와 워커 간 동기화 메시지
(gossip·mingle·heartbeat)를 전부 비활성화하고 남아 있던 `celeryev.*` 큐를 정리했습니다.
브로커 연결 상태 감시용 AMQP heartbeat(`broker_heartbeat`)는 역할이 다르므로 유지했습니다.

**결과** — 송신 트래픽 평균 **400kB/s → 3.2kB/s (약 99% 감소)**, 이벤트 큐 재생성 없이
정상 운영 확인.

![조치 후 — 송신 트래픽이 3.2kB/s 수준으로 감소](projects/medias/play/rabbitmq2.png)

### 2. 추론 요청을 Celery 큐에서 HTTP 동기 호출로 전환

**문제** — 오토 라벨링·스마트 라벨링의 추론 요청을 Celery 비동기 태스크로 처리하고
있었습니다. 하지만 추론은 작업자가 화면에서 결과를 기다리는 작업이라, **즉시 처리되지
않으면 의미가 없습니다.** GPU가 포화 상태일 때 큐는 이 요청을 거절하는 대신 쌓아두기만
해서, 과부하가 실패가 아니라 무한정 지연으로 나타났습니다. 작업자가 기다리다 이탈해도
워커는 이미 버려진 요청을 끝까지 연산하며 GPU를 점유했습니다.

**판단** — 큐는 지연을 감내할 수 있는 작업에 맞는 도구인데, 추론은 요청-응답 성격의
작업이라 브로커를 경유할 이유가 없었습니다. 결과를 기다릴 거라면 큐는 지연 구간만
하나 더 만드는 셈이고, 프로젝트마다 전용 워커가 늘어나는 구조(1번 문제의 원인)까지
그대로 떠안게 됩니다.

**조치** — 추론을 백엔드에서 추론 서버로 직접 HTTP 호출하는 구조로 전환했습니다.
GPU가 바빠 즉시 처리할 수 없으면 대기시키지 않고 곧바로 실패 응답을 내리고, 재시도는
백엔드가 담당해 클라이언트는 재시도 로직을 갖지 않습니다. 큐에는 지연을 감내할 수 있는
작업(이미지·라벨 썸네일 생성)만 남겼습니다.

**결과** — "무거운 작업은 큐"가 아니라 **"지연을 감내할 수 있는가"** 를 기준으로 통신
방식을 나눴습니다. 즉시성이 필요한 추론은 동기 호출로 빠르게 성공/실패를 확정하고,
그렇지 않은 작업만 큐에 남겨 프로젝트 증가에 비례해 늘어나던 추론 워커를 걷어냈습니다.
