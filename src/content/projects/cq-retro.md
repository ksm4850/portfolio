# 회고

이 프로젝트를 관통하는 키워드는 **"AI-네이티브"** 였다. 만드는 제품 자체가 AI 에이전트가
실험을 돌리는 도구였고, 그걸 만드는 방식도 AI(Claude Code)를 적극적으로 끌어들이는 것이었다.
회사의 다른 업무를 병행하면서 두 달 남짓 만에 core·relay·NATS·Supabase에 걸친 이 정도 범위를
쌓을 수 있었던 건, 프론트엔드 개발자와 둘이서 "AI를 어떻게 잘 쓸까"를 계속 실험한 덕이 크다.

## 좋았던 점

- **AI 활용 방식 자체를 팀의 자산으로 만들었다.** 단발성으로 AI에게 코드를 시키는 데서 그치지
  않고, 반복되는 작업을 스킬(워크플로우)로 정리했다. 스킬 본문은 agent-agnostic 마크다운
  단일 출처(`docs/skills`)로 두고, Claude Code·Codex 등 에이전트별 wrapper를 스크립트로 생성해
  일관성을 유지했다. `AGENTS.md`를 공통 진입점으로, 도메인별 규칙을 그 아래 두는 구조도 이 과정에서
  자리잡았다.
- **역할을 나눠 각자의 영역에서 AI 도입을 실험했다.** 프론트엔드는 디자인 프로토타이핑·프론트
  구현 가이드·셀프 리뷰 같은 스킬로, 나는 백엔드·인프라 쪽에서 스펙→구현→테스트 흐름과 특히
  **MCP E2E 테스트**에 AI를 붙였다. 서로의 시도를 공유하면서 "이건 AI에게 맡길 만하다 / 아니다"의
  감을 같이 키웠다.
- **제품을 사용자처럼 쓰는 테스트를 만들었다.** `cq-e2e-test`는 우리가 만든 MCP 도구를 AI가
  실제 사용자처럼 호출해 실험 생성→워커 실행→스냅샷→메트릭/아티팩트 수집까지 파이프라인 전체를
  종단 검증한다. 도구 이름·파라미터를 테스트에 하드코딩하지 않고 **런타임 tool description을 읽어
  호출**하게 해서, 제품이 바뀌어도 테스트가 잘 깨지지 않게 했다. 이건 "AI가 쓰기 좋은 인터페이스인가"를
  스스로 점검하는 장치이기도 했다.

## 아쉬운 점 / 다시 한다면

- **AI가 빠르게 만들어준 만큼, 내가 완전히 소화하지 못한 코드도 있었다.** 특히 직접 파고들지 않은
  영역은 "왜 이렇게 됐는지"를 나중에 다시 읽어야 했다. 속도와 이해의 균형을 초반에 더 의식적으로
  잡았어야 했다.
- **스킬·워크플로우를 정리하는 것 자체에도 비용이 든다.** 좋은 방식이지만, 아직 안정되지 않은
  부분까지 성급하게 스킬로 굳히면 오히려 수정 부담이 됐다. 무엇을 규칙으로 고정하고 무엇을 열어둘지
  구분하는 판단이 더 필요했다.

## 배운 점

- **AI를 잘 쓰는 것과 시스템을 이해하는 것은 별개가 아니다.** 경계(도메인 분리)와 규칙(스킬·
  AGENTS.md)이 명확할수록 AI도 더 정확하게 일했다. 결국 사람이 좋은 구조를 잡아둘수록 AI의
  생산성도 올라간다는 걸 체감했다.
- **AI가 쓰기 좋은 인터페이스가 곧 좋은 인터페이스다.** MCP 도구를 AI가 헷갈리지 않게 설계하는
  고민이, 사람에게도 명확한 API를 만드는 일과 같은 방향이었다.
- **혼자보다 함께 AI를 쓰는 게 훨씬 빨리 는다.** 각자 다른 영역에서 시도한 활용법을 공유하는 것만으로
  둘 다 학습 속도가 붙었다.
