# 서버 배포환경 ECS 전환

## 개요

입사 당시 회사 서비스들은 NCP의 여러 서버에서 Docker Compose로 운영되고 있었습니다.
어느 서비스를 어느 서버에 둘지는 사람이 리소스 여유를 보고 직접 정하는 수동 배치라
서버마다 유휴 리소스가 들쭉날쭉 남았고 그것이 고스란히 비용이었으며, 서비스를 추가할 때마다
배포·인증서·모니터링 구성을 반복해야 하는 불편함이 있었습니다.

![전환 전 — NCP 서버별 Docker Compose 운영](projects/medias/play/infra_ncp.png)

서버마다 Nginx를 따로 띄워 라우팅·인증서를 각자 관리했고, PostgreSQL도 서버별로
컨테이너로 운영되어 데이터 관리 지점이 흩어져 있었습니다. 외부 접근도 각 서버가
80/443과 ssh를 직접 노출하는 구조였습니다.

그러던 중 NCP 무료 크레딧이 소진되어 클라우드 이전이 불가피해졌고, 이전을 기회로
배포 환경 자체를 두 단계에 걸쳐 개선했습니다.

1. **AWS + Docker Swarm 통합** — 요금 최적화
2. **AWS ECS 전환** — 운영 편의성 (결과적으로 비용도 추가 절감)

## 1차: AWS + Docker Swarm 통합 — 요금 최적화

어차피 옮겨야 하는 상황에서, 수동 배치 구조를 그대로 복제하는 대신 소수의 EC2로 구성한
Swarm 클러스터에 전 서비스를 통합했습니다. 스케줄러가 리소스를 보고 컨테이너를 배치하니
사람이 서버별 여유를 계산하던 일이 없어지고, 유휴 리소스가 곧 줄어든 서버 수로 이어졌습니다.

**왜 Swarm이었나** — 모든 서비스가 이미 Docker Compose 기반이라, compose 파일과 거의
호환되는 Swarm 스택 파일로 옮기는 것이 가장 빠르고 리스크가 낮은 통합 방법이었습니다.

- **Traefik 단일 진입점** — 서버마다 각자 운영하던 Nginx를 없애고, 리버스프록시 +
  SSL 인증서 관리를 Traefik 하나로 통합 (도메인 라우팅을 라벨로 선언)
- **RDS 통합** — 서버별 PostgreSQL 컨테이너를 걷어내고 private 서브넷의 RDS로 일원화
- **네트워크 격리** — public/private 서브넷 분리, NAT 인스턴스 구성.
  서버마다 열려 있던 ssh는 OpenVPN 경유로 전환해 직접 노출 제거
- **Infisical** — 시크릿 중앙 관리 및 배포 시 주입
- **Portainer·dozzle + 모니터링 스택** — 컨테이너 상태 관리·모니터링·알림
- **배포 스크립트** — 스택/서비스 단위 배포 자동화 (config 해시 기반 변경 감지)

![1차 전환 후 — AWS Docker Swarm 클러스터](projects/medias/play/infra_swarm.png)

여러 서비스가 리소스를 공유하면서 서버 수를 줄였고, 라우팅·인증서·시크릿·DB 관리가
클러스터 단위로 일원화됐습니다.

## 2차: AWS ECS 전환 — 운영 편의성

Swarm으로 요금 문제는 풀었지만, 직접 운영해 보니 신경 써야 할 것이 많았습니다.
EC2 인스턴스 프로비저닝·패치, 서비스별 로깅 수집, Swarm 클러스터와 모니터링 스택 자체의
관리까지 — 전부 자체 운영 부담이었습니다. 장기 운영을 고려해 관리형 오케스트레이션인
ECS로 전환했습니다.

- **ECS Managed Instances** — Graviton(ARM) 인스턴스를 ECS가 자동 프로비저닝·패치.
  태스크 bin-packing으로 Fargate 대비 비용 절감
- **태스크별 로깅·모니터링 기본 지원** — 직접 꾸리던 로깅·모니터링을
  CloudWatch Logs/알람 + EventBridge → Dooray 웹훅 알림으로 대체
- **역할별 관리형 서비스로 대체** — Traefik → ALB + ACM 와일드카드 인증서,
  Swarm 볼륨 → EFS, Infisical → SSM Parameter Store
- **IaC (OpenTofu) 전면 도입** — 전 인프라를 코드로 정의, state는 S3 백엔드.
  기존 VPC·RDS·NAT는 소유하지 않고 참조만 하며 규칙만 덧붙이는 구조로 안전하게 공존
- **비용 최적화 장치** — RDS와 동일 AZ 단일 배치로 cross-AZ 전송비 회피,
  S3 게이트웨이 엔드포인트로 ECR pull의 NAT 요금 회피, NLB 대신 socat 프록시 EC2 운영

![2차 전환 후 — AWS ECS](projects/medias/play/infra_ecs.png)

### 설계에서 신경 쓴 점

- **시크릿이 state에 남지 않게** — 시크릿 값은 SSM에만 두고, IaC는 파라미터 이름/ARN만
  참조 (`with_decryption=false`)
- **이미지 배포와 인프라의 분리** — task definition에 `ignore_changes`를 적용해,
  애플리케이션 배포·스케일링을 IaC가 되돌리지 않도록 경계를 분리

### 작업 방식 — AI 협업

인프라를 전담해 본 경험이 많지 않은 상태에서, Claude Code를 적극 활용해 IaC 코드를
작성했습니다. 무엇을 관리형으로 대체할지, 비용을 어디서 아낄지 같은 방향 결정과
plan/apply·운영은 직접 담당하되, AI가 제안한 최적화(S3 게이트웨이 엔드포인트 등)는
그 원리를 학습해가며 검증 후 적용했습니다. 덕분에 혼자서도 짧은 기간에 전체 인프라를
코드화할 수 있었고, AI가 생성한 코드를 이해하고 검증해서 운영에 올리는 것 역시
개발자의 역량이라고 생각하게 된 경험이었습니다.

## 결과

- 전 서비스 ECS 이전 완료. 인스턴스 관리·로깅·모니터링이 관리형으로 넘어가
  직접 운영하던 영역이 크게 줄었고, 인프라 변경이 코드 리뷰·이력으로 추적 가능해짐
- 요금 최적화로 시작한 여정이었지만, ECS 전환 후에도 Graviton·bin-packing·전송비 회피
  장치들로 결과적으로 비용 절감을 유지(기존 비용 대비 20% 감소)
