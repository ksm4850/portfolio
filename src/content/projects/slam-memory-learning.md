# 메모리 뱅크 기반 자동 라벨링

## 개요

연구팀이 만든 메모리 뱅크 기반 자동 라벨링 모델을 **고객사 온프레미스 장비(GPU 서버 DGX-Spark 한 대)** 에서
서비스로 돌아가게 만든 작업입니다.

이 모델은 사람이 확정한 라벨을 기억(메모리 뱅크)해 두었다가, 새 이미지에서 찾은 객체를
기억과 비교해 "확정 / 거부 / 사람이 검수" 중 하나로 자동 판정합니다.
라벨링을 할수록 비교할 기억이 늘어나는 구조입니다.

- 담당: **모델을 서비스로 띄우는 구조 설계, 백엔드 연동, 캐싱, 배포** (모델 자체와 판정 로직은 연구팀 담당)
- 환경: 외부망과 끊긴 고객사 GPU 서버 한 대에 서비스 전체를 올리는 온프레미스
- 스택: Python, FastAPI, PostgreSQL, Redis, SQLite, Docker
- 기간: 2026.08 ~ 2026.10

## 1. 모델을 어떻게 나눠 띄웠나

**상황** - GPU 서버 한 대에서 여러 프로젝트를 동시에 돌려야 했습니다. 처음에는 모델 전부
(객체를 찾는 모델, 객체 특징을 뽑는 모델, 프로젝트별 기억, 검출 모델)가 한 덩어리였습니다.
이대로 프로젝트마다 띄우면 무거운 모델이 프로젝트 수만큼 GPU 메모리를 차지하고,
프로젝트별 기억이 서로 섞일 위험도 있었습니다.

**해결** - "모든 프로젝트가 같이 쓰는 것"과 "프로젝트마다 다른 것"을 나눠 컨테이너를 구성했습니다.


| 컨테이너      | 역할                                                       | 개수       |
| --------- | -------------------------------------------------------- | -------- |
| 공용 모델 서버  | 이미지에서 객체를 찾고(SAM3) 특징을 뽑는(DINOv3) 무거운 모델. 모든 프로젝트가 같이 사용 | 1개를 공유   |
| 프로젝트 컨테이너 | 프로젝트별 기억과 판정, 결과 캐시 보관                                   | 프로젝트당 1개 |
| 관리 서버     | 프로젝트 컨테이너 생성, 학습 시작, 새 모델 반영                             | 1개       |
| 학습 컨테이너   | 모델 학습만 하고 끝나면 종료                                         | 필요할 때만   |


무거운 모델은 GPU에 한 번만 올리고, 프로젝트가 늘어도 가벼운 프로젝트 컨테이너만 늘어납니다.
학습이 끝난 새 모델은 서비스를 멈추지 않고 프로젝트 컨테이너에 바로 교체합니다.

## 2. 관리 서버가 컨테이너를 직접 띄우는 방식 (DooD)

**상황** - 프로젝트 컨테이너는 프로젝트가 생길 때마다 하나씩 필요하고, 학습 컨테이너는 학습할 때만
잠깐 필요합니다. 미리 정해 두는 compose 파일로는 이렇게 그때그때 생기는 컨테이너를 관리할 수 없었습니다.

**해결** - 관리 서버 컨테이너에 호스트의 Docker 소켓을 연결해, 관리 서버가 호스트 Docker에 직접
명령하도록 했습니다(Docker-out-of-Docker). 이렇게 만든 컨테이너는 관리 서버의 자식이 아니라 같은
호스트의 형제 컨테이너라, 관리 서버가 죽어도 라벨링은 계속됩니다.

**신경 쓴 부분**

- **여러 번 요청해도 안전하게** - 관리 서버는 상태를 따로 저장하지 않습니다. 컨테이너 설정을 해시로
만들어 컨테이너 라벨에 붙여 두고, 다음 요청 때 지금 계산한 값과 비교합니다. 없으면 만들고, 같으면
그대로 두고, 다르면 새로 만듭니다.
- **이름이 아니라 라벨로 찾기** - 사람이 손으로 띄운 컨테이너를 관리 대상으로 오해하지 않도록,
관리 서버가 붙인 라벨로만 컨테이너를 찾습니다.
- **재시작은 Docker에 맡김** - 프로젝트 컨테이너에 자동 재시작 정책을 걸어, 관리 서버가 죽어도 Docker가
컨테이너를 살립니다. 관리 서버가 되살리는 일까지 맡으면 관리 서버 하나가 멈출 때 전체가 멈추기 때문입니다.
- **네트워크 자동 상속** - 관리 서버가 자기가 붙은 Docker 네트워크를 읽어 새 컨테이너에 그대로 붙입니다.
네트워크 설정이 두 곳에 나뉘어 있을 때 새 컨테이너만 다른 네트워크에 생겨 백엔드가 찾지 못하는
문제가 있어서, 정하는 곳을 하나로 모았습니다.
- **동시 요청 정리** - 같은 프로젝트의 컨테이너를 만드는 요청이 동시에 오면 충돌이 나서, 같은 프로젝트
요청은 순서대로 처리하게 했습니다.

## 3. 백엔드 연결 - 메시지 큐 대신 직접 호출

**상황** - 기존에는 백엔드와 모델 서버가 메시지 큐(Celery·RabbitMQ)를 거쳐 통신했습니다.
하지만 자동 라벨링은 작업자가 화면에서 결과를 기다리는 작업이라, 큐를 거치면 대기 단계만
하나 더 생깁니다. 장비 한 대 안에서 모두 도는 온프레미스라 중간에 큐를 둘 이유도 적었습니다.

**해결**

- 모델 서버를 HTTP API로 바꿔 백엔드가 직접 호출. 요청이 몰리면 컨테이너 안 대기열에서 순서대로 처리
- 백엔드와 모델 서버를 같은 Docker 내부 네트워크에 두고, 외부로는 포트를 열지 않음
- 주고받는 요청·응답 형식을 백엔드 한 곳에 정의해, 두 팀의 코드가 어긋나지 않게 함
- 프로젝트 컨테이너가 꺼져 있어도 확정한 라벨이 유실되지 않고, 자동 라벨링이 멈춘 채 남지 않게 처리

## 4. 캐싱 

**상황** - 라벨링은 같은 이미지를 여러 번 다시 보는 작업입니다. 그때마다 모델을 다시 돌리면
GPU 서버 한 대로 감당할 수 있는 양이 금방 한계에 닿습니다.

**해결** - 모델 결과를 저장해 두고, 같은 이미지가 다시 오면 저장된 결과를 씁니다.


| 저장하는 것             | 다시 계산하면 드는 비용 |
| ------------------ | ------------- |
| 객체 위치 (SAM3 결과)    | 약 1.5초        |
| 객체 특징 (DINOv3 결과)  | 150~300ms     |
| 검출 모델 결과           | 50~200ms      |
| 최근 이미지 (메모리)       | 이미지 다운로드·디코딩  |
| 모델 파일·변환된 엔진 (디스크) | 서버 시작 시 수 분   |


저장된 결과가 모두 있으면 무거운 모델을 아예 호출하지 않습니다.

**신경 쓴 부분**

- **모델이 바뀌면 옛 결과를 쓰면 안됨.** 이 문제는 에러 없이 조용히 틀린 결과를 내기  
때문에 발견하기 어렵습니다. 그래서 저장 키에 모델 버전을 넣어, 모델이 바뀌면 자동으로 새로 계산하게 했습니다.
- 메모리 캐시는 이미지 장 수가 아니라 **용량**으로 제한했습니다. 4K 이미지는 1080p보다 4배
가량 커서, 장 수로 제한하면 메모리 사용량을 예측할 수 없습니다. 너무 큰 이미지는 아예 저장하지
않아 한 장이 캐시 전체를 밀어내지 않게 했습니다.
- 이미지를 내려받는 동안 다른 요청이 기다리지 않도록 처리했습니다.

## 5. 배포

- **필요할 때만 뜨는 구조** - 장비가 켜지면 공용 모델 서버와 관리 서버만 뜨고, 프로젝트 컨테이너와
학습 컨테이너는 관리 서버가 필요할 때 만듭니다. 배포는 스크립트 하나로 통일했습니다.
