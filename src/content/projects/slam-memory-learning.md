# 메모리 뱅크 기반 자동 라벨링

## 개요

연구팀이 만든 메모리 뱅크 기반 자동 라벨링 모델이 **고객사 온프레미스 장비(GPU 서버 DGX-Spark 한 대)** 에서 서비스로 운영되도록 구성

- 모델 동작: 사람이 확정한 라벨을 기억(메모리 뱅크)해 두고, 새 이미지에서 찾은 객체를 기억과 비교해 "확정 / 거부 / 사람이 검수" 중 하나로 자동 판정
- 라벨링을 할수록 비교할 기억이 늘어나는 구조
- 담당: **모델을 서비스로 띄우는 구조 설계, 백엔드 연동, 캐싱, 배포** (모델 자체와 판정 로직은 연구팀 담당)
- 환경: 외부망과 끊긴 고객사 GPU 서버 한 대에 서비스 전체를 올리는 온프레미스
- 스택: Python, FastAPI, PostgreSQL, Redis, SQLite, Docker
- 기간: 2026.08 ~ 2026.10

## 1. 모델을 어떻게 나눠 띄웠나

**상황**

- GPU 서버 한 대에서 여러 프로젝트를 동시에 운영해야 함
- 초기에는 모델 전부(객체 탐지, 특징 추출, 프로젝트별 기억, 검출 모델)가 한 덩어리
- 프로젝트마다 띄우면 무거운 모델이 프로젝트 수만큼 GPU 메모리를 차지하고, 프로젝트별 기억이 섞일 위험

**해결** - "모든 프로젝트가 같이 쓰는 것"과 "프로젝트마다 다른 것"을 나눠 컨테이너 구성


| 컨테이너      | 역할                                                       | 개수       |
| --------- | -------------------------------------------------------- | -------- |
| 공용 모델 서버  | 이미지에서 객체를 찾고(SAM3) 특징을 뽑는(DINOv3) 무거운 모델. 모든 프로젝트가 같이 사용 | 1개를 공유   |
| 프로젝트 컨테이너 | 프로젝트별 기억과 판정, 결과 캐시 보관                                   | 프로젝트당 1개 |
| 관리 서버     | 프로젝트 컨테이너 생성, 학습 시작, 새 모델 반영                             | 1개       |
| 학습 컨테이너   | 모델 학습만 하고 끝나면 종료                                         | 필요할 때만   |


- 무거운 모델은 GPU에 한 번만 올리고, 프로젝트가 늘면 가벼운 프로젝트 컨테이너만 증가
- 학습이 끝난 새 모델은 서비스 중단 없이 프로젝트 컨테이너에 바로 교체

## 2. 관리 서버가 컨테이너를 직접 띄우는 방식 (DooD)

**상황**

- 프로젝트 컨테이너는 프로젝트 생성 시마다, 학습 컨테이너는 학습할 때만 필요
- 미리 정해 두는 compose 파일로는 동적으로 생기는 컨테이너 관리 불가

**해결** - 관리 서버 컨테이너에 호스트의 Docker 소켓을 연결해 호스트 Docker에 직접 명령 (Docker-out-of-Docker)

- 생성된 컨테이너는 관리 서버의 자식이 아닌 같은 호스트의 형제 컨테이너
- 관리 서버가 죽어도 라벨링은 계속 동작

**신경 쓴 부분**

- **멱등성 보장** - 관리 서버는 상태를 따로 저장하지 않음. 컨테이너 설정 해시를 라벨에 붙여 두고 요청 시 비교해 없으면 생성, 같으면 유지, 다르면 재생성
- **이름이 아닌 라벨로 조회** - 수동으로 띄운 컨테이너를 관리 대상으로 오인하지 않도록 관리 서버가 붙인 라벨로만 조회
- **재시작은 Docker에 위임** - 프로젝트 컨테이너에 자동 재시작 정책 적용. 관리 서버가 복구까지 맡으면 관리 서버 하나의 장애가 전체 장애로 이어지기 때문
- **네트워크 자동 상속** - 관리 서버가 자신이 붙은 Docker 네트워크를 읽어 새 컨테이너에 그대로 연결. 네트워크 설정이 두 곳에 나뉘어 새 컨테이너만 다른 네트워크에 생기고 백엔드가 찾지 못하던 문제를 설정 지점 일원화로 해결
- **동시 요청 직렬화** - 같은 프로젝트의 컨테이너 생성 요청이 동시에 오면 충돌하므로, 같은 프로젝트 요청은 순차 처리

## 3. 백엔드 연결 - 메시지 큐 대신 직접 호출

**상황**

- 기존에는 백엔드와 모델 서버가 메시지 큐(Celery·RabbitMQ)를 거쳐 통신
- 자동 라벨링은 작업자가 화면에서 결과를 기다리는 작업이라 큐를 거치면 대기 단계만 추가됨
- 장비 한 대 안에서 모두 도는 온프레미스라 중간에 큐를 둘 이유도 적음

**해결**

- 모델 서버를 HTTP API로 전환해 백엔드가 직접 호출. 요청이 몰리면 컨테이너 내부 대기열에서 순차 처리
- 백엔드와 모델 서버를 같은 Docker 내부 네트워크에 두고 외부 포트 미노출
- 요청·응답 형식을 백엔드 한 곳에 정의해 두 팀의 코드 불일치 방지
- 프로젝트 컨테이너가 꺼져 있어도 확정한 라벨이 유실되지 않고, 자동 라벨링이 멈춘 채 남지 않도록 처리

## 4. 캐싱

**상황**

- 라벨링은 같은 이미지를 여러 번 다시 보는 작업
- 매번 모델을 다시 돌리면 GPU 서버 한 대의 처리량이 금방 한계에 도달

**해결** - 모델 결과를 저장해 두고 같은 이미지 재요청 시 저장된 결과 사용


| 저장하는 것             | 다시 계산하면 드는 비용 |
| ------------------ | ------------- |
| 객체 위치 (SAM3 결과)    | 약 1.5초        |
| 객체 특징 (DINOv3 결과)  | 150~300ms     |
| 검출 모델 결과           | 50~200ms      |
| 최근 이미지 (메모리)       | 이미지 다운로드·디코딩  |
| 모델 파일·변환된 엔진 (디스크) | 서버 시작 시 수 분   |


- 저장된 결과가 모두 있으면 무거운 모델 호출 자체를 생략

**신경 쓴 부분**

- **모델 변경 시 옛 결과 사용 방지** - 에러 없이 조용히 틀린 결과를 내는 문제라 발견이 어려움. 저장 키에 모델 버전을 포함해 모델이 바뀌면 자동 재계산
- **메모리 캐시는 장 수가 아닌 용량으로 제한** - 4K 이미지는 1080p보다 약 4배 커서 장 수 기준으로는 메모리 사용량 예측 불가. 너무 큰 이미지는 저장하지 않아 한 장이 캐시 전체를 밀어내지 않도록 함
- **다운로드 중 대기 방지** - 이미지를 내려받는 동안 다른 요청이 기다리지 않도록 처리

## 5. 배포

- **필요할 때만 뜨는 구조** - 장비 기동 시 공용 모델 서버와 관리 서버만 실행, 프로젝트·학습 컨테이너는 관리 서버가 필요할 때 생성
- 배포는 스크립트 하나로 통일
