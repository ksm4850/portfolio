# 기술적 고민

### 1. 인증 — 사용자(웹·CLI)는 Supabase 세션, 워커는 NATS 인증
> 사용자는 웹·CLI 모두 같은 Supabase 세션을 쓰되 CLI는 device flow+PKCE로 안전하게 발급받고, 워커는 별도의 NATS 인증을 씀.

- **웹·CLI** — 둘 다 **Supabase 세션(JWT)** 기반. 단 CLI는 브라우저 리다이렉트 콜백을 직접 받기 어려워, 릴레이가 중개하는 **device flow**로 세션을 발급받음. 이 과정에 **PKCE(S256)** 를 적용(시크릿은 로컬에, 해시만 릴레이에)해, 승인 state만 유출돼도 시크릿 없이는 세션을 회수할 수 없게 함.
- **워커** — **NATS Auth Callout**으로 등록된 워커만 큐 접근. 접속 시 릴레이가 검증해 **워커 전용 권한으로 제한된 JWT를 즉석 발급**, 자기 subject 밖 pub/sub은 차단. NKey(Ed25519) 서명이라 private key는 나가지 않음.

### 2. 방화벽 뒤 워커 접근 — NATS 기반 토폴로지 역전
> 워커·릴레이 모두 NATS에 아웃바운드로만 연결해, 워커에 인바운드 포트 없이 원격 제어.

- **문제** — 워커는 집·사무실 PC라 공인 IP도 열린 포트도 없음. "서버가 워커로 접속"이 불가능.
- **결정** — 방향을 뒤집어 런타임 통신을 전부 NATS 위에서 처리. 에이전트 요청은 릴레이가 **request-reply**로 워커에 전달하고, progress·로그는 JetStream 스트림으로 흘림.
- **효과** — 워커는 아웃바운드만 되면 어디서든 동작. JetStream에 얹혀 있어 릴레이가 재시작·다운돼도 진행 중 실험이 죽지 않음.

### 3. 릴레이 상태 관리 — 실시간 상태와 이력의 저장소 분리
> 초 단위 상태는 Redis(TTL), 영속 이력은 PostgreSQL(bulk insert)로 분리해 무상태 수평 확장.

- **문제** — 하트비트·VRAM은 초 단위 갱신인데 매번 DB에 쓰면 부하만 크고 읽기도 느림.
- **결정** — 실시간 상태는 Redis에 TTL로(끊기면 자연 만료), 시계열 이력만 모아 PostgreSQL에 주기적 bulk insert.
- **효과** — 고빈도 I/O가 DB를 안 건드려 릴레이를 상태 없이 수평 확장, 대시보드 이력은 보존.

### 4. LLM이 짠 코드 안전 실행 — 하네스로 실행 경로 강제
> 에이전트의 실행 경로를 하네스로 좁혀, 임의 명령 없이 격리·재현 가능한 실행만 허용.

- **문제** — 워커 PC는 신뢰하지만 LLM은 통제 불가. 셸을 열어주면 임의 명령·추적 불가 실행 위험.
- **결정** — 셸은 조회 전용으로 제한(코드 실행·설치·파이프 우회 차단), 실제 실험은 config로 선언해 제출한 스펙대로만 실행.
- **효과** — 어떤 코드를 짜든 격리된 환경에서 배정된 GPU만 써서 결과가 자동 수집됨. run은 코드 스냅샷을 참조해 그대로 재현 가능.

### 5. 실험 지식 그래프 — 태그·계보·관계 + 하이브리드 검색
> 이름이 달라도 "가장 가까운 이전 실험"을 찾도록, 관계 그래프 + 어휘·의미 하이브리드 검색.

- **문제** — 실험이 수백 개면 "전에 해봤나"를 사람이 기억 못 함. 이름 검색은 표현이 조금만 달라도 놓침.
- **결정** — 관계를 3계층(태그·계보·관계 엣지)으로 모델링, 관계 추론은 사용자 측 LLM이 제안→사람이 확정. 검색은 어휘 유사도 + 임베딩 코사인 유사도를 **RRF**로 순위 합산.
- **효과** — 이름이 달라도 유사 실험을 찾아내, 같은 실험 반복을 줄이고 계보를 쌓음.
