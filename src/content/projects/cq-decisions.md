# 기술적 고민

### 1. 방화벽 뒤 워커에 어떻게 접근할 것인가 — NATS 기반 토폴로지 역전

**문제** — 워커는 사용자의 집·사무실 PC라 공인 IP도, 열린 인바운드 포트도 없다.
하지만 릴레이는 AI 에이전트의 요청을 받아 워커의 파일을 읽고 쓰고 셸을 실행해야 한다.
"서버가 워커로 접속"하는 일반적인 방향은 애초에 불가능하다.

**결정** — 워커가 릴레이에 붙는 게 아니라, **워커와 릴레이 모두 NATS에 아웃바운드로만 연결**하고
런타임 통신을 전부 NATS 위에서 처리하는 구조로 뒤집었다.

- 워커는 자기 전용 subject(`wp.worker.{id}.rpc`)를 구독하고, 릴레이는 에이전트의 MCP 요청을
  NATS **request-reply**로 변환해 그 subject에 던진다. 워커는 응답만 돌려준다.
- 실행 progress·디버그 로그처럼 흐르는 데이터는 JetStream 스트림
  (`JOB_PROGRESS`·`WORKER_STREAMS`)으로 워커가 발행하고 릴레이가 소비한다.
- REST는 워커 등록·sentinel 조회 같은 컨트롤 플레인에만 쓰고, 클라이언트(CLI·웹)→릴레이는
  WebSocket을 쓴다. 즉 **워커↔릴레이 경로에는 인바운드 포트가 하나도 필요 없다.**

**효과** — 워커는 아웃바운드 연결만 가능하면 위치·네트워크에 상관없이 동작한다. 또 통신이
JetStream에 얹혀 있어, 릴레이가 재시작·일시 다운되어도 진행 중인 실험이 죽지 않고 메시지가
유실되지 않는다(릴레이는 큐 디스패치·기록 게이트웨이일 뿐, 실행의 생명선이 아니다).

### 2. 인증 — Supabase 세션, PKCE, 그리고 워커 NATS 인증

세 종류의 주체(웹 사용자 · CLI · 워커)가 서로 다른 신뢰 모델을 가져서, 하나의 방식으로
묶지 않고 각 경로에 맞는 인증을 설계했다.

**웹 사용자** — Supabase Auth 기반. 별도 API 키 체계를 두지 않았다.

**CLI — PKCE로 로컬 콜백 탈취 방어** — CLI는 브라우저를 열어 로그인하고 로컬 콜백으로
세션을 회수한다. 이때 콜백 URL이나 state가 새면 토큰이 탈취될 수 있어 **PKCE(S256)** 를 적용했다.

- CLI가 `code_verifier`(랜덤 32바이트)를 만들어 **로컬에만 보관**하고, 그 SHA-256 해시인
  `code_challenge`만 릴레이에 등록한다.
- 로그인이 끝난 뒤 토큰을 회수하는 `/auth/device/check` 단계에서 `code_verifier`를 함께
  제시해야만 검증을 통과한다. state 문자열 하나가 유출돼도 verifier 없이는 토큰을 가져갈 수 없다.

**워커 — NATS Auth Callout으로 등록된 워커만 큐 접근** — NATS 큐에 아무나 붙으면 다른
사용자의 실험 명령을 볼 수 있다. NATS를 operator/JWT 모드로 운영하고 **Auth Callout**으로
인증을 릴레이에 위임했다.

- 워커는 권한이 전부 deny된 **sentinel 유저**의 JWT와, 등록 시 발급받은 `connect_token`으로
  접속한다. sentinel은 "APP 계정으로 라우팅해 auth callout을 트리거"하는 용도의 더미라
  비밀 값이 아니다.
- NATS가 접속을 릴레이(`$SYS.REQ.USER.AUTH`)로 넘기면, 릴레이가 `connect_token`으로 DB에서
  워커를 검증하고 **그 워커 전용 권한으로 제한된 JWT를 즉석 서명**해 돌려준다. NATS가 sentinel
  JWT를 이 워커별 JWT로 교체하며 연결을 허용한다.
- Operator→Account→User 3단계 JWT 계층 + NKey(Ed25519) 서명으로, 워커는 자기 subject
  바깥으로는 pub/sub이 막힌다. 신원 증명 시 private key는 네트워크에 나가지 않는다.

### 3. 릴레이 상태 관리 — Redis 실시간 상태와 PostgreSQL 이력의 분리

**문제** — 워커 하트비트·가용 VRAM·GPU 사용률은 초 단위로 갱신된다. 이걸 매번 PostgreSQL에
쓰면 쓰기 부하만 커지고, 정작 "지금 이 워커가 살아있나"를 읽는 건 느려진다. 반대로 시계열
이력은 대시보드 그래프를 위해 영속적으로 남겨야 한다.

**결정** — 성격이 다른 두 데이터를 저장소로 분리했다.

- **실시간 상태 → Redis만.** `worker:status:{id}` 해시에 status·free_vram·heartbeat를 담고
  **TTL 60초**를 건다. 하트비트가 끊기면 키가 자연 만료돼 별도 정리 없이 오프라인이 드러난다.
  온라인 워커 조회도 Redis sorted set으로 끝낸다.
- **시계열 메트릭 → PostgreSQL.** 워커별 최신 스냅샷을 메모리에 모아 **30초마다 bulk insert**
  한 번으로 밀어넣어 쓰기 횟수를 줄인다.
- **수평 확장 대비 singleflight.** 릴레이를 여러 대로 띄우면 bulk insert가 중복 실행될 수 있어,
  Redis `SET NX`(시간 버킷 키)로 **한 인스턴스만 flush를 수행**하도록 조정했다. 단 Redis 오류
  시엔 "멈추는 것보다 일시적 중복이 낫다"는 원칙으로 통과시킨다.

**효과** — 고빈도 상태 읽기/쓰기가 DB를 건드리지 않아 릴레이를 상태 없이 수평 확장할 수
있고, 대시보드 이력은 그대로 보존된다.

### 4. LLM이 짠 코드를 안전하게 실행하기 — 하네스로 실행 경로 강제

**문제** — 워커 PC 자체는 유저가 직접 설치한 유저 소유라 신뢰할 수 있다. 통제할 수 없는 건
**AI 에이전트(LLM)** 다. 에이전트가 MCP로 코드를 직접 작성하고 실험까지 돌리기 때문에, 셸을
자유롭게 내주면 임의 명령으로 워커 PC를 건드리거나, 실험을 추적·재현이 안 되는 형태로 제멋대로
돌려버릴 수 있다.

**결정** — 에이전트가 "코드를 실행하는 경로"를 하네스 하나로 좁히고, 그 바깥의 임의 실행을 막았다.

- **bash 도구는 조회 전용으로 제한** — 에이전트에게 주는 `bash`는 `nvidia-smi`·`ls`·`df` 같은
  조회에만 쓰게 하고, 코드 실행(`python`·`node`·`./`·`go run` …)과 패키지 설치(`pip install`·
  `npm install` …) 패턴을 차단 목록으로 막는다. `cat train.py | python` 같은 파이프 우회도 차단하고
  타임아웃은 30초로 묶는다. 즉 에이전트는 bash로 코드를 못 돌린다.
- **코드 실행은 하네스 경로로만** — 실제 실험은 `create_job → create_run → start_job`을 거쳐야 하고,
  이때 실행 명령·아티팩트 경로·GPU 수 등을 **config로 선언**해야 한다. 임의 실행이 아니라 선언된
  스펙대로만 돌아간다. 의존성도 `pyproject.toml`에 적으면 하네스가 uv로 설치하므로 임의 설치가 필요 없다.
- **하네스가 실행을 격리·표준화** — preflight로 엔트리 파일·쓰기 권한·의존성·GPU 가용성을 먼저
  검증하고, GPU Pool로 물리 GPU를 run 단위로 배타 확보해 `CUDA_VISIBLE_DEVICES`로 배정된 GPU만
  노출한다. run마다 별도 디렉토리에서 실행하고 타임아웃으로 무한 실행을 끊는다.
- **결과 자동 수집 + 재현성** — 종료 후 산출물을 스캔·중복 제거해 업로드하고 상태를
  QUEUED→RUNNING→DONE/FAILED로 전이시킨다. run은 특정 코드 커밋(스토리지 기반 content-addressed
  스냅샷)을 참조해 실행되므로 "그때 그 코드"를 그대로 되돌려 돌릴 수 있다.

**효과** — 에이전트가 어떤 코드를 짜든, 선언된 config대로·격리된 디렉토리에서·배정된 GPU만 써서·
결과가 자동 수집되는 **통제된 봉투 안에서만** 실행된다. 임의 명령으로 워커 PC를 건드리거나 실험이
추적 불가능하게 새어나가는 걸 원천 차단한다.

### 5. 실험 지식 그래프 — 태그·계보·관계와 하이브리드 검색

**문제** — 실험이 수백 개 쌓이면 "이거 전에 해봤나", "이 실험이 저 실험의 개선인가"를 사람이
기억할 수 없다. 이름으로만 찾으면 표현이 조금만 달라도 놓친다.

**결정 (1) — 관계를 3계층으로 모델링.** 태그(키워드를 카테고리로 묶음) · 계보(`parent_job_id`) ·
관계 엣지(improves/compare/derives 등)로 나눴다. 관계 추론은 서버가 아닌 **사용자 측 LLM**이
수행해 제안(suggested)하고 사람이 확정(confirmed)/거부(rejected)한다. 대칭 관계는 canonical
방향으로만 저장해 중복을 막는다.

**결정 (2) — 임베딩을 비동기 파이프라인으로.** 실험 내용이 바뀌면 임베딩이 stale 상태가 되고,
이를 Supabase Edge Function(`embed-jobs`)이 주기적으로 처리한다. **stale job을 원자적으로
선점(lease)** 한 뒤 OpenAI `text-embedding-3-small`(1536차원)로 임베딩해 bulk로 반영하고,
실패는 일시/영구를 구분해 재시도한다. 요청 경로가 아닌 백그라운드에서 도는 덕에 실험 생성이
임베딩 지연에 묶이지 않는다.

**결정 (3) — 검색은 하이브리드(lexical ⊕ semantic) + RRF.** `search_resources_hybrid` RPC가
두 랭킹을 합친다.

- **Lexical** — 이름과 **태그 키워드**를 `pg_trgm`의 `word_similarity`로 매칭한다.
  오타·부분 일치·표현 차이에 강하고, 어떤 태그가 걸렸는지(matched_tags)를 근거로 돌려준다.
- **Semantic** — 쿼리 임베딩과 실험 임베딩의 코사인 거리(`<=>`, pgvector)로 의미 유사도를 잡는다.
- **RRF(Reciprocal Rank Fusion)** — 두 랭킹의 순위를 `Σ 1/(60 + rank)`로 합산해 최종 순위를
  낸다. 점수 스케일이 다른 두 신호를 순위만으로 안전하게 섞고, 결과마다
  lexical/semantic/lexical+semantic 매칭 근거를 표시한다.

**효과** — 새 실험을 만들기 전에 "가장 가까운 이전 실험"을 이름이 달라도 찾아낼 수 있어,
같은 실험 반복을 줄이고 실험 계보를 쌓아갈 수 있다.
