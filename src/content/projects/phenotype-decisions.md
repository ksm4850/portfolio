# 기술적 고민

### 1. Google Health 수집 - 덮어쓰기 기반 스케줄링 동기화
> 증분 병합 대신 매번 통째로 다시 받아 덮어써, 실패해도 다음 실행에 저절로 복구.

- **구조** - Google Health는 데이터를 직접 조회해 가져와야 해서 스케줄링으로 동기화. **매시**에는 오늘 데이터를 다시 받아 갱신하고, **새벽**에는 완료된 어제를 확정(최근 2일을 겹쳐 훑어 누락 보완).
- **이유** - 하루 데이터는 하루 안에서 append-only라, 통째로 받아 덮어쓰면 항상 완전한 하루가 됨. 병합 로직이 필요 없고 실패해도 다음 실행에 자가 복구.
- **연동** - OAuth 동의 흐름은 state에 서명해 위변조를 막음. 기기를 뒤늦게 연동하거나 재연결한 경우 과거 구간을 소급 수집.

### 2. 시계열 대량 수집 - TimescaleDB + 청크 INSERT
> hypertable·압축 정책으로 저장하고, bind 파라미터 상한을 고려해 나눠서 대량 INSERT.

- **문제** - 참가자 기기마다 센서·이벤트가 끊임없이 쌓이고, 업로드 한 번에 수천 건이 들어옴.
- **결정** - 이벤트 테이블을 TimescaleDB hypertable로 두고 오래된 청크에 압축 정책 적용. INSERT는 PostgreSQL bind 파라미터 상한(32,767)을 넘지 않게 행을 나눠 대량 실행하고, 요청 JSON 파싱은 orjson으로 전환.
- **효과** - 대량 업로드를 안정적으로 처리하면서 저장 용량 증가를 억제.

### 3. 수집 타임라인 API - 레인 단위 캐시
> 캐시 단위를 "레인 조합"이 아닌 "레인 하나"로 잡아, 새로 켠 레인만 계산.

- **문제** - 타임라인은 여러 센서·웨어러블 레인을 같은 시간 버킷에 올려 한 번에 응답. 켜진 레인 조합 단위로 캐시하면 레인이 n개일 때 조합이 2ⁿ개로 폭발하고, 레인 하나만 바꿔도 전부 다시 계산.
- **결정** - 레인별로 캐시하고 응답 시 합침. 수집이 끊긴 구간은 표시와 지표 계산 양쪽에서 끊어서 처리.
- **효과** - 새로 켠 레인만 계산하고, 끊긴 구간 때문에 앱 사용 시간이 부풀던 문제를 없애며 계산 속도도 개선.

### 4. 고객 지표 산출 - 지표 정의를 DB에서 관리
> 지표의 이름·설명·근거 원자료를 DB에서 관리해, 지표를 추가해도 클라이언트 수정 불필요.

- **결정** - 원자료를 일 단위 지표로 서버에서 계산해 제공. 지표 정의는 DB에 두고 클라이언트는 정의를 받아 그대로 렌더링.
- **효과** - 새 지표가 생겨도 서버 쪽 계산만 추가. 신체활동·수면 지표의 근거는 Google Health 웨어러블 데이터로 연동.

### 5. 설문/EMA - 응답 시각 기준 회차 판정
> 설문 원본과 연구-설문 연결을 분리하고, 응답 가능 시간 안의 응답만 해당 회차로 인정.

- **모델** - 설문 원본과 연구-설문 연결을 분리해 같은 설문을 여러 연구에서 재사용. 알림 시각마다 응답 가능 시간(windowMinutes)을 두고 응답 시각 기준으로 회차를 판정.
- **기록** - 부분 응답, 종료 방식, 진입 경로를 함께 기록.
- **보호** - 응답이 있는 설문은 수정·삭제를 막고 soft delete로 처리해 수집된 응답과 설문 구조가 어긋나지 않게 함.
